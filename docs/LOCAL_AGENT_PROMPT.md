# Prompt for the local agent

Copy everything between the rules below into a fresh Claude Code session running
on the Windows machine that has Steam and Project Zomboid Build 42.20 installed.

---

Ты работаешь локально на Windows-компьютере, где установлен Steam и Project
Zomboid Build 42.20. Кодовая часть уже реализована. Не переписывай проект с
нуля. Твоя задача — провести реальные live-тесты, исправить только
подтверждённые несовместимости и довести release candidate до подтверждённого
v1.0.0.

## 0. Что уже сделано, и почему тебе не нужно это переписывать

Проект писался в удалённом контейнере без игры. Там реализовано всё, что можно
реализовать без запущенного Project Zomboid: протокол, файловый IPC, Lua-мост,
исполнитель команд, семнадцать игровых адаптеров, sidecar, MCP-сервер, planner,
голосовой слой, автономный режим, установщик и Windows-сборка. Юнит- и
контрактные тесты зелёные, но **ни одна строка не выполнялась внутри игры**.

Отсюда единственное, чего там не могло быть: подтверждения, что имена и
сигнатуры игровых API Build 42.20 совпадают с тем, что объявлено в адаптерах.
Часть предположений помечена комментарием `-- Build 42:`:

```
grep -rn "Build 42:" pz-mod/
```

**Это не исчерпывающий список.** Команда возвращает шесть строк в двух файлах,
а `docs/GAME_API_VERIFICATION.md` помечает `requires_live` пятьдесят два
символа — то есть grep покрывает примерно восьмую часть неподтверждённого.
Полный перечень — в этом документе; grep удобен, чтобы быстро прыгнуть к
комментарию, но не для того, чтобы решить, что символ в порядке, раз его там
нет. Почти каждый провал первого живого прогона будет одним из пятидесяти двух.

## 1. Прочитай перед тем, как что-либо запускать

В этом порядке:

1. `docs/LOCAL_GAME_HANDOFF.md` — что реализовано, что проверено без игры, что
   требует игры, точные пути, как понять, что мод загрузился и sidecar
   подключился.
2. `docs/LIVE_TEST_PLAYBOOK.md` — двадцать сценариев S01–S20: подготовка мира,
   команда запуска, обязательные postconditions, признаки ошибки.
3. `docs/LOCAL_DEBUG_MAP.md` — таблица «симптом → модуль → лог → действие».
4. `docs/GAME_API_VERIFICATION.md` — каждый используемый игровой API, его
   предполагаемая сигнатура и поле для фактического результата.
5. `docs/PROGRESS.md` — текущее состояние работ.
6. `AGENTS.md` — инварианты проекта. Один из них определяет всё остальное:
   **результат может быть `succeeded` только тогда, когда наблюдаемое
   постусловие это доказывает.**

## 2. Развернуть

```
git fetch --all --prune
git checkout feature/playable-agent-1.0
git pull --ff-only

install.bat
doctor.bat
backup-save.bat
start.bat
status.bat
```

`doctor.bat` должен найти установку игры, каталог `Zomboid`, каталог обмена и
сообщить о capability surface. Если он этого не делает — останавливайся здесь и
чини это, прежде чем идти дальше: все последующие сценарии читают те же пути.

## 3. Тестовый сейв

**Не используй основной сейв.** Создай отдельный тестовый мир и сними резервную
копию до первого запуска:

```
backup-save.bat
pz-agent backup-save --list
```

`pz-agent restore-save` отказывается работать при запущенной игре. Это не
неудобство, а защита: восстановление поверх открытого сейва уничтожает его.

Проверь, что резервная копия действительно читается, до того как агент получит
право действовать:

```
pz-agent backup-save --list
```

## 4. Прогон сценариев

```
run-live-tests.bat
```

Он идёт по S01–S20 последовательно и возобновляем. Один сценарий:

```
run-live-tests.bat --scenario S07_NESTED_INVENTORY
```

Состояние и текущая таблица:

```
pz-agent live-test status
```

Продолжить с первого непройденного:

```
resume-live-tests.bat
```

## 5. Что делать после каждого FAIL

По порядку, без пропусков:

1. Собери evidence: `collect-evidence.bat --scenario S<nn>_<NAME>`.
2. Найди **конкретную** причину. `docs/LOCAL_DEBUG_MAP.md` даёт первый адрес;
   `console.txt` даёт Lua-ошибку, которой больше нигде нет.
3. Исправь ровно её. Не рефактори вокруг, не «улучшай» соседний код.
4. Добавь regression-тест, который падает на старом коде и проходит на новом.
5. Повтори сценарий.
6. Обнови соответствующую строку в `docs/GAME_API_VERIFICATION.md`: статус и
   фактическая сигнатура.

**PASS не ставится без postcondition evidence.** Runner это проверяет, и
`result.json` защищён хешем содержимого — отредактировать его руками нельзя, и
попытка будет обнаружена на `finalize`. Если хочется поставить PASS, а
доказательства нет — значит сценарий не прошёл.

Запрещённые способы «починить» тест: ослабить постусловие, сделать проверку
необязательной, поймать исключение и объявить успех, отметить сценарий
пройденным вручную. Постусловие, которое проходит, ничего не наблюдая,
превращает каждый последующий PASS в догадку.

## 6. Что тебе разрешено менять

Разрешено:

- имена и сигнатуры игровых API в адаптерах и в `Toolkit.lua`;
- `required_symbols` и capability-пробы, когда символ называется иначе;
- поведение, которое опровергнуто настоящим живым тестом;
- добавление regression-тестов;
- документацию, чтобы она соответствовала найденному.

Не нужно и не следует:

- проектировать архитектуру заново;
- переписывать sidecar loop, MCP-сервер, action engine, planner, policy,
  installer, схемы IPC или тестовую инфраструктуру;
- переписывать основную реализацию Lua-адаптеров — правь сигнатуры, а не
  структуру;
- дописывать TeamON abstraction — интерфейс уже есть, нужен только рабочий
  endpoint;
- собирать проект вручную из кусков.

Если кажется, что переписать проще, — почти наверняка это симптом того, что
причина ещё не найдена. Вернись к шагу 2 из раздела 5.

## 7. После того как все двадцать сценариев PASS

1. Endurance 30 минут: `run-live-tests.bat --scenario S19_AUTONOMOUS_30_MIN`.
2. Endurance 2 часа: `run-live-tests.bat --scenario S20_AUTONOMOUS_2_HOURS`.
3. Проверка восстановления сейва: восстанови резервную копию и убедись, что мир
   открывается.
4. `collect-evidence.bat` — собрать всё.
5. `finalize-release.bat` — построить `release/evidence-manifest.json` с SHA-256
   по каждому артефакту. Он откажется, если чего-то не хватает, и назовёт чего.
6. `python scripts/check_release.py --release` — гейт, который сейчас падает и
   обязан падать, пока нет манифеста с живыми доказательствами.
7. Только теперь: merge в `dev`, затем в `main`, тег `v1.0.0`, GitHub Release с
   ZIP и его SHA-256.

Порядок именно такой. Тег ставится после того, как доказательства собраны, а не
до.

## 8. Как отчитываться

В финальном ответе: branch, commit, ссылка на CI, ссылка на релиз, SHA-256 ZIP,
таблица S01–S20 со статусами, измеренные p50/p95 задержки (наблюдаемые, не
оценочные), путь к `release/evidence-manifest.json`.

Если что-то не прошло — так и напиши, с указанием сценария и причины.
Незавершённый прогон, описанный честно, полезнее выдуманной таблицы PASS:
на выдуманной кто-то построит следующий шаг.

## Notes for whoever hands this over

The prompt above is self-contained. Two things are worth saying out loud to the
person running it:

- **The remote stage deliberately did not tag v1.0.0.** The release gate
  (`scripts/check_release.py --release`) fails today, on purpose, because
  `release/evidence-manifest.json` does not exist. That failure is the design
  working, not a broken build.
- **The branch is `feature/playable-agent-1.0` and it was not merged.** Merging
  is the local agent's last step, after evidence exists.
